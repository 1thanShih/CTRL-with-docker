# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This repo is a Dockerized ROS Noetic workspace for a small autonomous vehicle (DLV) that performs lane following, turn detection, and sign-based maneuvers, driving an Arduino-controlled motor base. **Target platform: Raspberry Pi 4 (4GB), ARM64, headless** — no rviz, no X11. The host (Pi) builds and runs a container; `catkin_ws/` is bind-mounted in, so source edits on the host are picked up immediately inside the container.

## Container Workflow

All ROS commands run **inside** the container — the host doesn't have ROS installed.

```bash
make             # build image + run container (foreground zsh)
make attach      # open a second zsh in the running container
make stop        # stop + remove container
make clean       # stop + remove image
make logs        # follow container logs
```

The container is started with `--rm`, so it disappears on exit. The image is named `ros-noetic-zsh:latest`; the container is named `ros-noetic-zsh`. The container runs `--privileged --net=host` because it needs udev access (for `/dev/ttyUSBx` device remapping) and ROS multicast on the host network.

Two bind mounts:
- `./catkin_ws` → `/root/catkin_ws` — source edits picked up live.
- `~/.claude` (host) → `/root/.claude` — Claude Code credentials persist across container restarts. Log in once with `claude login` and the auth survives.

### Build / source inside the container

`scripts/entrypoint.sh` already runs `catkin_make` and sources the workspace on container start. After editing C++ code or adding/removing packages or msg files, rebuild:

```bash
cd /root/catkin_ws && catkin_make && source devel/setup.zsh
```

Python-only changes do **not** require a rebuild (scripts are installed via `catkin_install_python`), but adding a new `.msg` field does — message headers/Python bindings are generated by `catkin_make`.

### Hardware device remapping

On container start, the entrypoint copies `scripts/*.rules` into `/etc/udev/rules.d/` and reloads udev so USB devices appear at stable symlinks:
- `/dev/arduino` (from `scripts/arduino.rules`)
- `/dev/camera` (from `scripts/camera.rules`)

Some launch files still hardcode `/dev/ttyUSB0` rather than the symlinks — fix at the launch-file level when encountered.

### Claude Code inside the container

The image installs Node.js LTS + `@anthropic-ai/claude-code` globally. Inside the container:

```bash
claude --version    # smoke test
claude login        # first run only; creds persist via the ~/.claude bind mount
claude              # interactive
```

## Architecture

### Package layout (`catkin_ws/src/`)

Only the production packages live here. Everything else has been moved to `legacy/` (see below).

- **`lane_follower/`** — perception + control core. Three pipeline stages communicate via topics:
  1. `lane_detect_v2.py` subscribes to `/camera/image_raw`, publishes lane `offset`/`angle` on `lane_detect` as `LaneData`, and a debug image on `lane_detect/image_out`.
  2. `turn_detect.py` subscribes to the same image, publishes `TurnDetect` (with `turn_direction`, `pixel_size`, `offset`) describing the largest detected directional triangle/sign.
  3. `lane_controller_fuzzy.py` consumes both, runs a hand-rolled fuzzy controller, and publishes `geometry_msgs/Twist` on `arduino_vel`.
- **`arduino_mega_ctrl/`** — Python helpers (e.g., `move_straight_5s.py`) that publish `Twist` to drive the motors via rosserial.
- **`sensors/camera/`** — camera driver / publisher (publishes `/camera/image_raw`).

Note: the `rosserial` packages used at runtime are installed system-wide via apt in the Dockerfile (`ros-noetic-rosserial-python` etc.) — there is no `rosserial` package under `src/`.

### `legacy/` (sibling of `catkin_ws/`, NOT built)

Preserved for reference only. Never symlinked into the workspace, never sourced by catkin:

- `legacy/lane_follower_v1/` — old `lane_detect.py` (v1) and PD `lane_controller.py`.
- `legacy/simple_twist_publisher/` — small C++ Twist publisher (test/demo).
- `legacy/sensors_rplidar_ros/` — RPLidar driver (hardware not in current build).
- `legacy/dlv_bringup/` — old top-level bringup that referenced packages not in this repo.

### Main launch file

`lane_follower/launch/lane_detect_bringup.launch` is the integrated entrypoint: it starts rosserial → Arduino, the camera, `lane_detect_v2`, `turn_detect`, and `lane_controller_fuzzy`. Tunable params (turn thresholds, hard-turn angular velocity/duration for the first vs second turn, sign-detect thresholds, cooldown) are set in this file and are the primary tuning surface — recent commits have all been parameter tweaks here.

### Custom messages

`lane_follower/msg/`:
- `LaneData`: `float32 offset`, `float32 angle`
- `TurnDetect`: `string turn_direction`, `float32 pixel_size`, `float32 offset`

When changing these, every node that produces/consumes them must agree, and `catkin_make` must be rerun before Python imports of `lane_follower.msg.*` work.

## Conventions

- Comments and log messages in this repo are mixed Chinese + English — match the surrounding style when editing.
- v1 lane code lives under `legacy/lane_follower_v1/`. Prefer v2 (`lane_detect_v2.py`) for all changes; treat the legacy files as read-only history.
- The bringup launch uses `lane_controller_fuzzy.py`. The legacy PD `lane_controller.py` is **not** API-compatible with the v2 detector — don't try to unify them.
- Image is headless: `opencv-python-headless`, no X11, no rviz. Do not add GUI deps back.
